AI service desk

AI Service Desk + Infrastructure Snapshot Platform

This project is a Microsoft Azure starter architecture for a configuration-aware Level 1 service desk. The design keeps the Copilot-facing agent separate from the infrastructure collector, so the AI can use approved evidence without holding every platform credential.

01 · Intent

A support agent needs evidence, not direct keys to everything

The project starts with a practical service desk problem. A user might say, “My VPN is not working,” but a useful answer needs more than generic troubleshooting. The agent may need approved knowledge, device state, policy assignments, security-agent health, and history.

Instead of letting the AI call every vendor API directly, this architecture places an evidence layer between the conversation and the infrastructure platforms.

AI Service Desk Copilot Studio, SharePoint knowledge, ITSM sources, vendor documentation, and conversation flow.
Infra Snapshot API A controlled API that returns normalized device, policy, difference, freshness, and history evidence.
Snapshot Platform Scheduled collectors, raw blob archive, Azure SQL current state, temporal history, and retention cleanup.

02 · Why two projects

Conversation and collection have different risk profiles

A service desk agent and a large infrastructure collector do not need to be the same workload. The agent needs fast, explainable evidence. The collector needs credentials, pagination, throttling, retry logic, raw response storage, data normalization, and operational history.

  • Security: Copilot does not receive every infrastructure platform credential.
  • Reliability: the last successful snapshot remains useful during vendor outages.
  • Performance: support flows read a fast database instead of waiting for multiple live APIs.
  • Ownership: infra teams own collectors; automation or ITSM teams own the agent experience.

03 · Project 1

AI Service Desk foundation

The AI Service Desk deployment script creates the Azure and Power Platform foundation: resource group, Key Vault, private storage, configuration container, Function App, managed identity, Entra security group, and a Power Platform sandbox when the Power Platform CLI is available. 

cd ai-service-desk
chmod +x deploy-ai-service-desk.sh
./deploy-ai-service-desk.sh

# foundation only:
# Copilot Studio topics, SharePoint grounding,
# screenshot model integration, and ITSM flows
# are intentionally future implementation steps.

04 · Project 2

Infrastructure Snapshot Platform

The snapshot platform is designed to collect weekend snapshots from systems such as Jamf, Intune, Defender, Qualys, CyberArk, Forescout, Zscaler, and Symantec DLP. It stores original responses in Blob Storage, normalized current state in Azure SQL, and temporal history for comparison. 

cd infra-snapshot-platform
chmod +x deploy-infra-snapshot.sh

export SQL_ADMIN_PASSWORD='Use-A-Temporary-Strong-Password'
./deploy-infra-snapshot.sh

05 · History model

Current state plus 62-day memory

The database schema creates current tables for devices, policies, and assignments with system-versioned temporal history. It also tracks source systems, snapshot runs, checkpoints, raw object references, configuration changes, and live refresh requests.

  • Devices: current device identity, user, platform, compliance, management status, and check-in.
  • Policies: current policy name, type, scope, enabled state, and payload reference.
  • Assignments: include/exclude targets and policy-object relationships.
  • ConfigurationChanges: detected differences with optional retention hold.

06 · Controlled freshness

Read snapshots first, refresh live only when needed

The snapshot database is a fast operational cache, not the final source of truth. A support case can use stored evidence when it is fresh enough, then request live refresh only for a specific user, device, or policy when the situation requires it.

Design guardrail

The Function App currently returns connector placeholder responses by design. It deploys the scheduling, storage, SQL, and orchestration foundation without inventing vendor-specific permissions or API behavior.

07 · Security model

A safer AI boundary

The security principle is read-only first. Secrets belong in Azure Key Vault, not JSON files, shell scripts, Git, or Copilot instructions. The AI should call approved API operations, not every original platform. Sensitive fields should be removed before data reaches the agent.

  • No raw secrets in configuration files.
  • Managed identity where supported.
  • Live refresh protected with stronger authorization and auditing.
  • Separate DEV, TEST, and PROD environments.
  • The original management platform remains authoritative.

08 · Deployment path

Build the evidence layer before the agent depends on it

The recommended order is to deploy the snapshot platform, apply the SQL schema, configure one connector, run a test snapshot, validate database and history, protect the Infra API, then connect the AI Service Desk foundation to that evidence layer.

This is a foundation starter, not a finished Copilot Studio solution. That is the right boundary for this stage: infrastructure first, approved evidence next, then the user-facing conversation design.
