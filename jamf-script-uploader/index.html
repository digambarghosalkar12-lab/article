Jamf Script Uploader: API-Safe Script Deployment for Jamf Pro

Jamf Script Uploader is a focused macOS shell utility for administrators who need to upload scripts into Jamf Pro without turning a simple operational task into a risky copy-paste routine.

Project article · Jamf Pro · OAuth · macOS shell · API Client · script upload

View project on GitHub

Article index

Problem
Uploading scripts manually can create naming conflicts, unclear failures, and unsafe credential habits.
Approach
Prompt for credentials at runtime, validate the selected file, timestamp the Jamf name, and upload through the API.
Stack
bash, curl, plutil, base64, sed, osascript, Jamf OAuth, and the Classic Scripts endpoint.

01 · Why

A small tool for a repeatable admin task

Jamf Pro script upload is often part of day-to-day endpoint operations: packaging a remediation script, placing it in Jamf, and then attaching it to a policy. The task is simple, but the surrounding details matter. A wrong script type, reused name, missing permission, or copied secret can slow down the work or create avoidable risk.

Jamf Script Uploader wraps that flow into one interactive macOS utility. It asks for the Jamf tenant, API Client ID, and Client Secret, lets the admin choose a local script, validates the file, appends a timestamp, uploads it, and returns the Jamf script name and ID when Jamf provides one.

02 · Flow

Credentials in, validated script out

The workflow is intentionally direct. The administrator enters a Jamf Pro base URL, authenticates with OAuth client credentials, chooses a script type, selects the local file, and gives the script a display name. The tool creates a final name using a local timestamp in YYYYMMDD_HHMMSS format so repeated uploads do not collide. 

Jamf Pro URL
API Client ID and Client Secret
Script type: Shell, Bash, Zsh, Python, Perl, or Ruby
Local file selection
Display name + timestamp
Upload to Jamf Pro
Return final name and Jamf script ID

03 · Security

Runtime secrets, least privilege, and HTTPS by default

The security choices are practical. The Client Secret is requested when the script runs, terminal echo is disabled for the secret prompt, credentials are not written to a configuration file, the Jamf URL must use HTTPS, and sensitive variables are cleared on exit.

  • Use a dedicated Jamf API Client instead of a broad administrator account.
  • Assign only the API Role permissions needed for scripts: Create Scripts, with Read Scripts recommended for verification.
  • For unattended use, retrieve secrets from an approved vault or CI secret store rather than hardcoding them.

04 · API design

Modern token flow, classic script creation endpoint

The tool uses Jamf Pro OAuth client credentials to obtain a bearer token, then submits a Classic API script object to create the script. The request includes a name, filename, priority, category, blank optional metadata, and Base64-encoded script contents. 

POST /api/v1/oauth/token
grant_type=client_credentials

POST /JSSResource/scripts/id/0
Authorization: Bearer token
Content-Type: application/xml

Upload defaults are deliberately conservative: category is None, priority is After, info and notes are blank, and parameters 4 through 11 are left empty.

05 · Validation

A quick check before the API call

Before uploading, the selected type must match the file extension or the first-line shebang. Shell, Bash, Zsh, Python, Perl, and Ruby are supported selections. The tool also checks that the selected file exists and is readable before encoding and sending it.

Operator note

Jamf stores the script content. It does not install Python, Perl, Ruby, or any missing interpreter on target Macs. The selected type helps validate the source file and create the Jamf filename, but the fleet still needs the right runtime.

06 · Troubleshooting

Clear failures beat silent upload problems

The utility reports HTTP status codes and Jamf response bodies so admins can see whether the issue is authentication, authorization, URL format, certificate trust, proxy behavior, or file validation.

  • 401 usually points to a wrong Client ID, stale Client Secret, disabled API Client, or incorrect tenant.
  • 403 means the API Client authenticated but the API Role does not have permission to create scripts.
  • 404 often means the user entered a path instead of the Jamf base URL.
  • SSL errors should be fixed through certificate, proxy, and trust review rather than insecure curl flags in production.

07 · What this solves

Safer script deployment without a heavy platform

The value of this project is its shape: small enough to audit, narrow enough to understand, and useful enough for daily Jamf work. It removes repetitive upload friction while keeping the sensitive pieces visible and controlled.

For endpoint teams, that means cleaner script names, predictable upload defaults, least-privilege API access, and a clear success result that can be recorded in change notes or deployment tickets.
