MRR: A Meeting-Aware macOS Restart Reminder for Jamf Pro

MRR—macOS Restart Reminder—is a configuration-driven restart workflow for managed Macs. It combines a lightweight LaunchDaemon, Jamf Pro Custom Settings, and swiftDialog to encourage routine restarts without dropping an avoidable interruption into the middle of a call.

Long-running Macs need maintenance restarts, but blunt reminders can interrupt meetings or give administrators too little control.

01 · Why

Restart compliance is a user-experience problem too

Restarting a Mac clears stale processes, completes some updates, and gives support teams a cleaner operating baseline. The technical action is simple; the timing is not. A reminder that arrives during a customer call creates friction, while a prompt that can be dismissed forever does not improve fleet health.

MRR treats the restart as a small managed workflow rather than a single pop-up. Jamf defines the policy, launchd provides dependable execution, swiftDialog presents the user interface, and a local state file remembers the current boot, used snoozes, and next eligible prompt.

02 · Architecture

One daemon, one controller, and managed intent

The LaunchDaemon com.mrr.restartreminder starts at load and every five minutes. Its controller runs as root, reads com.mrr.restartreminder from Managed Preferences, calculates full days since the last boot, discovers the console user, and launches swiftDialog inside that user's GUI session. 

Jamf Custom Settings
        ↓
com.mrr.restartreminder preferences
        ↓
LaunchDaemon checks every 5 minutes
        ↓
uptime + user + snooze + meeting state
        ↓
normal reminder → snooze or restart
        ↓
forced countdown after snoozes are exhausted

The controller exits quickly when the workflow is disabled, the uptime threshold has not been reached, no interactive user is present, a snooze is still active, or swiftDialog is unavailable. That keeps the recurring job cheap and makes disabling the experience a configuration change rather than a daemon-removal exercise.

03 · Configuration

The profile controls policy and presentation

The included Custom JSON Schema turns the preference domain into editable Jamf controls. Administrators can set a restart frequency with a one-day minimum, snooze count and interval, countdown duration, button labels, messages, icons, banners, window persistence, and the enabled state.

  • Normal and forced windows have independent width and height controls.
  • Title and message fonts can define name, size, weight, and colour through swiftDialog font parameters.
  • Title and message alignment can be set independently to left, centre, or right.
  • Numeric settings are validated again at runtime, so a malformed local plist cannot bypass schema minimums.
  • Boolean values are normalized explicitly instead of depending on shell-specific case modifiers.

04 · Meetings

Wait for the call, not just the app

Simply seeing Teams, Zoom, Webex, or FaceTime open is not enough to suppress a reminder; these applications often remain running all day. MRR requires a supported conferencing process plus a stronger activity signal: an active audio-input engine or a conferencing-related power assertion.

When a meeting is detected, the daemon exits and checks again five minutes later. It does not create a long fixed deferral, so the reminder can return soon after the call ends. Focus and Do Not Disturb are intentionally ignored because those modes are not reliable proof of a live meeting.

Force-restart choice

Forced restart waits for an active meeting by default. Jamf administrators can enable IgnoreMeetingDuringForceRestart when policy requires the countdown to proceed even during a call. Meeting detection remains best-effort because macOS does not expose a stable system-wide meeting-status API.

05 · Escalation

Snooze first, then make the final state explicit

While snoozes remain, the normal window offers Restart Now and a configurable snooze action. Persistent mode keeps the window on top, limits accidental keyboard dismissal, and reopens unexpected closures without spinning forever; repeated dialog failures stop until the next daemon cycle.

Once snoozes are exhausted, a separate forced window shows an unblurred countdown. Restart occurs only when swiftDialog returns the documented Restart-button or timer-expiry code. A crash or unexpected exit is logged and cancels that restart attempt rather than treating a UI failure as permission to reboot.

At the final restart point, MRR tears down the logged-in user's GUI domain, force-kills remaining user processes if required, clears its own logs, and calls the system restart. This is deliberately forceful: the article and interface should make clear that unsaved work can be lost after the final allowance is consumed.

06 · Deployment

Readable Jamf scripts instead of opaque payloads

The install script is self-contained, but its controller and plist are plain-text cat heredocs. Jamf administrators can audit or tailor them directly without decoding Base64. The installer writes the controller and LaunchDaemon, applies root ownership and expected modes, bootstraps the daemon, enables it, and starts the first check. 

/usr/local/bin/mrr-restart-reminder
/Library/LaunchDaemons/com.mrr.restartreminder.plist
/Library/Application Support/MRRRestartReminder/state.plist
/var/log/mrr-restart-reminder.log

sudo ./install.sh
sudo ./uninstall.sh

A separate generator asks for the Jamf install-script, uninstall-script, and schema asset filenames. It displays the expected format, validates each name, and emits a synchronized dist set from the maintained controller, plist, schema, and uninstaller sources.

07 · Operations

Small safeguards make the workflow supportable

  • The state resets when the boot epoch changes, preventing snooze counts from leaking into a new uptime cycle.
  • Managed log locations are restricted to simple filenames under /var/log because the daemon writes as root.
  • Unexpected forced-dialog exit codes never trigger a restart.
  • The uninstaller unloads the job and removes the controller, plist, state, local preferences, and logs; MDM profile scope is removed separately in Jamf.
  • The generated and maintained payloads are syntax-checked and compared during development to prevent installer drift.

08 · What this solves

A restart policy that fits the shape of a workday

MRR gives endpoint teams a transparent middle ground between optional reminders and abrupt reboot commands. The fleet gets a defined uptime threshold, bounded deferrals, measurable escalation, and a final enforcement path. Users get clear messages, predictable snoozes, meeting-aware timing, and presentation that can match organizational language and design.

Most importantly, the project stays understandable. It is a shell controller, a plist, a schema, and readable deployment scripts—not a hidden service. That makes the behavior easier to audit, test with a small smart group, adapt to policy, and support when real Macs behave differently from a lab.
